# 漫威电影风格标注分镜

## 目标

把基础分镜信息拆解为可执行的导演级逐镜方案，并输出下游提示词节点可直接解析的文字版 JSON；不要输出表格截图、分镜图片或只有人类可读的普通段落。用户提供场景图片时，将图片纳入空间和视觉连续性设计。先建立剧情 Beat、空间规则和动作因果，再决定镜头；不按句切镜、不默认九宫格、不预设镜头数量或等分时长。

“漫威电影风格”在本 Skill 中指超级英雄商业电影常见的清晰叙事、群像接力、英雄感建立与拆解、喜剧停顿、能力递进和视效预演逻辑。不得照搬现有影片的具体角色、镜头或台词。

## 输入门槛

### 首轮检查

先检查当前对话和附件，不重复索取用户已经提供的内容。基础分镜信息是必需项，场景图片是可选项：

1. **基础分镜信息**：至少包含场景/段落、发生的事件或动作、出场角色、开场状态、结束结果。对白、目标时长、画幅、情绪和制作限制可选；用户没有提供画幅时直接采用 21:9，不要追问。
2. **场景图片（可选）**：可以是实景照、概念图、场景设计图、勘景照或已建立的场景参考帧。用户提供图片时，应尽量判断每张图片对应哪个场景。

基础分镜信息达到最低要求后即可生成，不得因未提供场景图片而停止或追问。没有图片时，根据文字建立可拍的空间与视觉方案，并把新增的空间、美术、光线和摄影设定标注为“推定设计”。基础分镜信息不足时先停止拆镜并索取缺失内容；不要在没有剧情动作时只凭图片编故事。

使用以下最小收集模板；用户可自由书写，不强迫填写表格：

```text
请补充：
1. 基础分镜：场景名称/编号、剧情与动作、角色、开场状态、结束结果；
2. 可选增强：场景图片，并注明“图片A对应场景S1”；
3. 其他可选项：对白、总时长、画幅、人物/道具参考、风格侧重、禁用项。
```

### 收件确认

基础分镜达到最低要求后，在内部完成以下确认；仅在存在会改变剧情或镜头结果的歧义时提问：

- 基础分镜覆盖了哪些场景和剧情 Beat；
- 若有图片，每张图片与 `sceneRef` 的对应关系；
- 角色、道具、对白、时长和制作限制是否明确；
- 若有图片，文字与图片是否在地点、时代、天气或空间结构上直接冲突。

若映射明确，直接生成，不增加确认轮次。

## 可选场景图片约束

### 建立场景视觉圣经

用户提供场景图片时，只依据图片中可见信息，为相应场景内部提取：

- 时间感、时代、天气和环境状态；
- 入口、出口、主要轴线、纵深、垂直层级、通行路径、遮挡和危险区；
- 建筑结构、材质、固定物、可见道具及其相对位置；
- 主光来源与方向、色温、明暗对比、主色和环境色；
- 前中后景、视觉焦点、可用构图边界和氛围；
- 可参与动作的真实环境元素，以及无法从图片确认的事项。

不要把图片中偶然出现的人或物自动升级为剧情角色或关键道具。不要推断图片外的剧情、声源、威胁或房间结构；必要推断必须标为“推定设计”。

### 继承规则

- 用户提供场景图片后，图片是相应 `sceneRef` 的视觉硬约束，不是可选氛围参考。
- 同一场景的所有镜头须继承空间结构、建筑材质、关键物件位置、主光方向、色彩与气氛。
- 近景和特写的背景仍须来自同一空间，不得切成无来源的通用背景。
- 只有与某图片对应的镜头才继承该图，不把一张图强行套给无关场景。
- 图片与通用风格词冲突时，以图片的可见视觉事实为准。
- 用户明确剧情与基础分镜决定“发生什么”；已有图片决定“这个场景看起来怎样、空间如何组织”。若两者对场景身份直接冲突，先询问用户，不擅自覆盖。

没有场景图片时，依据文字中的地点、时代、天气、道具和动作方向建立空间规则；缺失的视觉事实可以合理设计，但必须在 `narrativeBeats` 或相关镜头 `note` 中写明“推定设计”。同一场景仍须保持空间结构、物件位置、主光方向、色彩和氛围连续。

## 拆镜工作流

按以下顺序思考，最终只输出规定 JSON：

1. **场景诊断**：判断场景类型、核心任务、人物关系变化、观众最终必须记住的信息，以及动作、喜剧、悬疑、群像、情绪或混合属性。
2. **剧情 Beat**：先拆建立、进入、异常、判断、应对、失败、升级、变招、解决、拆解/回落和钩子等叙事段落，再分配镜头。
3. **空间规则**：有图片时把场景视觉圣经转成空间规则；无图片时从文字和必要的推定设计建立入口、出口、轴线、人物初始位置、运动方向、危险来源、可利用物件、前中后景和空间重置点。
4. **动作因果**：每条动作遵循“意图 → 执行 → 结果 → 反应 → 下一步变化”。保证观众看见危险、理解方向、感到重量并看到结果。
5. **风格模块**：选一个主模块，最多两个辅助模块；不要把所有模块同时堆入一场戏。
6. **逐镜设计**：每镜承担一个明确叙事任务，给出景别、机位与有动机的运镜、可拍画面、对白、调度、声音、时长和导演标注。
7. **连续性检查**：检查轴线、视线、动作接点、道具位置、光向、伤势、角色状态和场景图继承。

## 风格模块

- **群像接力**：A 的动作结果引向 B，B 再给 C 制造机会；同一时刻只保留一个主要视觉中心。
- **喜剧打断**：动作升级 → 英雄姿态 → 突然停顿 → 讲话或荒诞行为 → 留白 → 环境或对手打断 → 动作继续。
- **英雄感建立/拆解**：先建立宏大姿态，再用故障、误判、拆台或狼狈结果拆解。
- **能力展示递进**：先展示局部规则，再组合使用，最后到极限展示。
- **延迟揭示**：声音 → 环境变化 → 他人反应 → 局部 → 轮廓 → 全貌 → 第一次攻击。
- **现实感动作**：强调身体重心、真实环境物、失败、调整、受伤和打击结果；近景感受动作，全景看懂动作。
- **情绪回落**：减少切换和运镜，允许沉默，让高强度段落留下余波。

用户未指定侧重时，先按场景内容选择适用模块；总体调性可参考 60% 科幻冒险与人物接力、20% 喜剧拆解、20% 经典清晰动作逻辑。单人场景不得强套群像接力，严肃场景不得强加喜剧打断。默认比例只是兼容内容时的设计方向，不要写成对具体影片的复制。

## 镜头规范

- 不机械地把每句文字变成一镜；镜头数量由叙事清晰和动作可读性决定。
- `type` 写景别，如大全景、全景、中景、中近景、近景、特写、主观镜头。
- `movement` 写“机位 + 运镜 + 动机”，不能只列术语。例如：`低机位手持后退跟拍，为保持冲锋角色与出口同轴可读`。
- `description` 必须是可拍画面，包含主体、所在空间、轴线或前中后景、动作方向、危险来源或视觉焦点；有场景图片时还须体现图片约束。
- `content` 只放该镜头的对白原文；无对白时必须为 `""`，不得概括或改写用户对白。
- `characters` 只列镜头内实际可见或明确画外发声的角色。
- `props` 只列本镜头叙事或动作实际使用的道具，不把全部场景陈设重复列入。
- `action` 写表演、调度、群像焦点转移和动作因果。
- `sound` 写对白之外的环境音、撞击、停顿、音乐节奏点或声音桥；无依据时不要虚构剧情性声源。
- `durationSec` 每镜必填，按信息密度、动作复杂度、对白和停顿分配，不平均切分。
- `sceneRef` 每镜必填；同场连续镜头保持一致，换场时更新。
- `note` 至少含一个功能标签，并说明设计逻辑和衔接。复杂动作/视效镜头补充 Previs、Techvis、Postvis 及实拍、替身、机械装置、CG 的衔接建议。
- `mergedMembers` 仅在同场连续镜头确实适合合并为 15 秒内组合镜头时使用；常规情况不要输出该键。

可用功能标签：`【空间建立】【人物进入】【危险预警】【信息揭示】【人物判断】【动作意图】【执行动作】【结果确认】【疼痛反馈】【人物反应】【空间重置】【动作接力】【英雄感建立】【英雄感拆解】【喜剧标点】【背景笑点】【能力规则】【能力升级】【反派揭示】【情绪停顿】【关系变化】【段落收束】【下一场钩子】`。

信息不足时可补充摄影、调度和声音设计，但须在 `note` 或 `narrativeBeats` 中标注“推定设计”；不得改动用户给定的剧情结果。

## 画幅规则

- 用户明确指定画幅时，以用户指定值为最高优先级；否则固定使用 `21:9`。
- 把最终画幅写入根级 `projectConstraints`，格式为：`画幅比例：21:9；按超宽银幕构图适配，不生成实体黑边。`
- 每个镜头的 `note` 都须保留简短跨镜标记：`项目约束（跨镜）：画幅比例 21:9。` 用户改为其他画幅时同步替换。
- `description` 按最终画幅设计人物横向站位、负空间、前中后景和运动路径。21:9 不能只作为标签存在。
- 画幅是交付比例，不得在画面中生成上下黑条、黑框或遮幅实体。

## 提示词节点兼容协议

输出必须符合项目 `StoryboardOutput` 协议，使用规范英文键名。截图中的中文列名只用于理解含义，不要把结果输出成截图或仅含中文表头的普通文本。

- 根对象固定包含 `shots`、`narrativeBeats`、`projectConstraints`。
- 每镜固定包含 `id`、`shotNo`、`sceneRef`、`type`、`movement`、`durationSec`、`description`、`content`、`sound`、`note`。
- 为便于提示词节点挂载资产，每镜同时保留 `characters`、`props`、`action`；无内容时分别使用 `[]`、`[]`、`""`。
- `id` 使用从 1 开始连续递增的数字；`shotNo` 使用稳定文字编号，如 `S1-01`、`S1-02`。
- `sceneRef` 对应截图“场景”列，优先保留用户场次；可规范为 `01场｜夜｜维修舱`。同场镜头必须完全一致，换场才更新。
- `type` 对应“景别”，`movement` 对应“运镜”，`description` 对应“画面描述”，`content` 对应“台词”，`sound` 对应“音效”，`note` 对应“备注”。
- `durationSec` 必须是纯数字秒数，例如 `5` 或 `3.5`，禁止写成 `"5秒"`。
- 无对白时 `content` 必须为 `""`；无音效时 `sound` 必须为 `""`。不要使用中文键 `台词`、`音效` 替代规范键。
- `description` 负责截图“画面描述”中的可拍信息；摄影机焦段等明确参数可写入 `movement` 或 `note`，不得只写抽象剧情。
- 输出纯文字 JSON，不添加 Markdown 表格、代码围栏、标题、解释、结语或省略号。

## 输出协议

基础分镜未达到最低要求时，输出索取信息的普通中文。基础分镜达到最低要求后，无论是否有场景图片，默认只输出一个合法 JSON 对象，不加 Markdown 代码围栏、标题、解释或结语。参考截图的文字版协议为：

```json
{
  "shots": [
    {
      "id": 1,
      "shotNo": "S1-01",
      "sceneRef": "01场｜夜｜维修舱",
      "type": "全景",
      "movement": "机位、运镜及动机",
      "durationSec": 5,
      "description": "按21:9设计的可拍画面、空间轴线；有图片时写明视觉继承",
      "content": "",
      "characters": ["角色名"],
      "props": ["剧情道具"],
      "action": "表演、调度与动作因果",
      "sound": "环境音、效果音、停顿或声音桥",
      "note": "【空间建立】风格逻辑、衔接和制作提示；项目约束（跨镜）：画幅比例 21:9。"
    }
  ],
  "narrativeBeats": [
    "S1｜场景诊断：核心任务与关系变化｜主风格模块｜视觉节奏｜空间轴线；无图补全项标注推定设计",
    "S1-B1｜建立空间与人物位置",
    "S1-B2｜动作升级并产生结果"
  ],
  "projectConstraints": [
    "画幅比例：21:9；按超宽银幕构图适配，不生成实体黑边。"
  ]
}
```

保证 JSON 可解析：使用双引号，不留注释、尾逗号、`undefined` 或 JSON 外文本。若用户明确要求 Markdown 表格、自然语言分镜或其他既有系统协议，保持同样的拆镜逻辑，再按用户格式输出。

## 输出前自检

1. 是否完整使用了基础分镜信息；若有场景图片，是否正确映射并继承？
2. 场景任务与结束变化是否明确？
3. 入口、出口、轴线、运动方向和必要的空间重置是否可读？
4. 每个动作是否包含意图、执行、结果、反应，环境是否参与动作？
5. 角色是否有不同的动作方式和反应，群像是否通过接力而非抢画面？
6. 喜剧是否先建立期待再拆解，并保留停顿？
7. 能力和视效是否服务剧情，真人、替身、实拍和 CG 的关系是否清楚？
8. 景别、运镜、时长和节奏是否有变化，高强度之后是否有余波？
9. 同一 `sceneRef` 的材质、道具位置、主光方向、色彩和氛围是否连续；有图片时是否忠于图片，无图片时新增设定是否标注“推定设计”？
10. 每镜固定字段是否齐全，对白是否准确，JSON 是否可解析并能被提示词节点识别？
11. 根级 `projectConstraints` 与每镜 `note` 是否使用同一画幅；用户未指定时是否均为 21:9？
